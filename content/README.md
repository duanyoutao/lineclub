# 修改档案内容

[`archives.json`](archives.json) 是页面与 TXT 下载共用的档案数据。修改内容无需编辑 TypeScript；`src/data.ts` 只保留类型和阵列位置映射。

## 文件结构

- `categories`：检索筛选器的五个分类，按显示顺序排列。“全部档案”由界面添加，无需填写。
- `columns`：三维阵列从左到右的五个分类。与 `categories` 包含相同名称，顺序可以不同。
- `records`：全部档案，编号从 `X-001` 起连续排列。每个分类至少一份、最多二十份，同分类在数组中的顺序决定列内顺序。

| 字段                        | 内容                                                        |
| --------------------------- | ----------------------------------------------------------- |
| `id`                        | 稳定编号，用于收藏、定位和下载文件名                        |
| `title`、`en`               | 中文标题、英文标题                                          |
| `department`、`category`    | 科室、所属分类；分类须与上面的名称完全一致                  |
| `date`、`lead`、`clearance` | 编目范围、相关人物、访问范围；`RESTRICTED` 对应目录访问状态 |
| `abstract`                  | 摘要                                                        |
| `findings`                  | 至少一条研究记录，使用字符串数组；可写 `[文字](https://…)` 链接 |
| `source`                    | 设定参考的完整 HTTP 或 HTTPS 链接                           |
| `sections`                  | 可选。长文章节，用于「阅读全文」浮层，见下文                |
| `substrate`                 | 可选。该档案专属的信息基板图案，见下文「逐文档基板图案」    |

## 文本格式

正文只支持四种写法，其余字符按纯文本显示：

| 写法                        | 效果                             |
| --------------------------- | -------------------------------- |
| `[文字](https://example.com)` | 可点击链接，仅接受 http 与 https |
| `**重点**`                  | 加粗                             |
| `*强调*`                    | 斜体                             |
| `` `代码` ``                | 等宽片段                         |

在摘要与章节段落这类块级位置，**空行会分成两个段落**，单个换行是换行符。代码片段内部的符号保持原样，不参与其他解析；HTML 特殊字符一律转义，写 `<b>` 只会显示成文字。

下载的 TXT 会去掉这些标记：`**重点**` 变成 `重点`，链接保留为 `文字 (https://example.com)`，因此纯文本依然完整可读。

不支持列表、标题、表格、引用与行内图片 —— 列表用 `points`，章节标题用 `heading`，图片用 `figures`。校验要求标记成对出现，落单的反引号或 `**` 会被拒绝。

## 长文章节

`abstract` 与 `findings` 是每份档案都有的摘要，适合一两屏。更长的内容写在可选的 `sections` 里，它会出现在详情页的「阅读全文」浮层中：

```json
"sections": [
  {
    "heading": "章节标题",
    "paragraphs": ["第一段，可以写得很长，也可以包含 `代码` 与 **重点**。", "第二段单独一条。"],
    "points": ["要点一", "要点二"],
    "figures": [{ "src": "media/archive.jpg", "caption": "图片说明" }]
  }
]
```

单条 `paragraphs` 字符串内部也可以用空行分段，两种写法等效。

- 每章必须有 `heading`，并且在 `paragraphs`、`points`、`figures` 中至少有一项。
- `figures[].src` 只能是 `public/media/` 下的图片路径，**文件必须真实存在**，否则校验直接失败。只有放进 `public/media/` 的素材才会进入构建产物。
- 章节上限 24 章。
- 不写 `sections` 的档案与旧版完全一致，页面与下载文本都不会变化。

## 逐文档基板图案

档案盒的信息基板默认是一块素色扩散板。可选的 `substrate` 让**某一份档案**在自己的模型上换成指定图案，其它档案不受影响：

```json
"substrate": "marks/rhodes-island.webp"
```

- 路径只能是 `public/marks/` 下的图片，**文件必须真实存在**，否则校验失败。
- 图案按自身比例居中铺在基板上，不拉伸；透明区域会被裁掉（`alphaTest`），所以带透明背景的 PNG / WebP 最合适。
- 实现方式是在基板正面叠一层贴图平面，而不是给模型贴图 —— 程序化生成的模型没有 UV 坐标，这与档案标签的做法一致。
- 因为基板在磨砂盖板之后，这层用的是**不透明材质 + alpha 裁切**而非半透明：WebGL 的屏幕空间折射只解析玻璃后的不透明几何。

上表中除 `sections` 外均必填，文本不能只包含空白。引号按 JSON 规则写为 `\"`，换行写为转义形式。保留公开设定的来源，区分档案式改写与游戏原文。

## 修改与验证

1. 编辑 JSON 中对应档案的字段。修改分类名称时，同时更新 `categories`、`columns` 和各档案的 `category`。
2. 执行 `npm run export:archives`，校验数据并更新 `public/archives/` 中的下载文件。校验失败时不会写入任何下载文件。
3. 执行 `npm run check:content` 检查校验规则与下载一致性，再运行 `npm run build` 验证构建。将 JSON 与更新后的 TXT 一起提交。
4. 在 `npm run dev` 中查看标题、详情、检索和下载结果，尤其检查长标题与较长正文的实际布局。

`npm run dev` 启动前和 `npm run build` 构建前都会自动校验并导出。开发服务器运行期间，JSON 修改会更新页面；下载文件需再次执行 `npm run export:archives` 或重启开发服务器。

阵列的五列与原片布局相连，分类数量仍固定为五个。每列可容纳一至二十份档案；超过二十份会与相邻列的槽位冲突，校验会拒绝。编号必须从 `X-001` 起连续，不要通过交换或重编号档案改变顺序，以免已有收藏指向不同内容。校验可以检查编号格式与排列，无法判断改写后是否仍是原来那份档案。

内容分离的建议来自 [@Tomahawkd 的 PR #3](https://github.com/LBEILC/RhineLabUI/pull/3)。此实现仅拆分当前项目的档案数据、校验和导出。
